# local content storage delivery

The first local implementation stores payload parts, progress, sealed file
descriptors and retention under BBG's existing Database owner. Cybergraph can
stream a Blob and atomically publish its retention with an application head.
Fjall/SSD and redb/HDD exercise the same content API.

| Cybergraph | `597d09127b6237b3b8afdb1855ae817e220caf23` | [[cybergraph/audit/storage/content-2026-09-24/README|Commands, source closure and integration tests]] |

The linked receipts record the executable commands and revisions for all
observations: out-of-order upload/resume, exact Blob identities, large streamed
input, conflicting retries, competing heads, process exits, corruption and
injected redb write/sync failures. They include dependency locks and log checksums.

The [project tracker](../../roadmap/storage/README.md) marks S2/S3/S4/S7 as
implementing. The [acceptance matrix](../../roadmap/storage/acceptance.md#current-local-evidence)
maps the exercised subset to A rows; none is fully qualified.

The remaining delivery is substantial: canonical structural identity/range
proofs, Radio's injected source/sink path, release/leases/GC, content-aware
migration and replication, FS naming/patch semantics, product APIs and Vault
restore. Existing application-only migration refuses content it cannot carry.
Sealed files remain protected indefinitely until their complete reclamation
protocol is implemented. There is no new Radio store or public file identity.

This receipt covers local feature-branch inputs, not a release candidate. Both
profiles ran on APFS solid-state storage. Physical power-loss, disk-full,
performance and privacy qualification remain open. Existing Blob compatibility
does not settle the stack's final identity construction.
